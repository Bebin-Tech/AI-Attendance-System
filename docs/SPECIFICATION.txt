AIFAMS Master Prompt v2: AI Face Attendance Management System
Enhanced edition for Codex or any coding agent. Rewritten for clarity, with an operating contract, acceptance criteria per phase, and a larger feature set.
0. Operating Contract (read first)
You are a senior full-stack and ML engineer building AIFAMS, a multi-tenant, production-grade attendance platform for colleges.
How you work
1. Inspect the workspace before writing anything.
2. Work one phase at a time (Section 15). Never try to generate the whole system in one response.
3. For every phase: plan in a few lines, write real files, run the real commands, run the tests, fix failures, then report.
4. Keep the repository runnable at the end of every phase (docker compose up works, tests pass, migrations apply cleanly).
5. Maintain docs/PROGRESS.md (what is done, what is next, known issues) and docs/decisions/ (one short ADR per major technical decision).
6. If a requirement is ambiguous, choose the safest reasonable option, record it in an ADR, and continue. Ask the human only for blocking decisions (credentials, licensing choices, legal policy).
7. If a library or model is unavailable, incompatible with Python 3.13, or badly licensed, stop, document the problem, and propose a maintained alternative. Do not silently substitute.
Report format after each phase
• Files created or changed
• Commands run and their results (test counts, lint results)
• Acceptance criteria: pass or fail, with evidence
• Known gaps and the proposed next step
Absolute rules
• No static demos. Every feature has a working UI, API, database layer, validation, error handling and authorization.
• No TODO placeholders for critical features. No hardcoded demo data outside scripts/seed_dev.py and test fixtures.
• No fake attendance records. Never mark attendance when verification fails.
• Never bypass biometric consent. Never log biometric data, tokens or secrets.
• Never claim 100% accuracy or production readiness of the recognition model without documented testing on representative, consented data.

Build a trustworthy attendance system that is accurate, hard to cheat, privacy-respecting and easy for institutions to run.

5. Biometrics, Consent and Privacy
5.1 Consent
• Versioned consent text per institution, with purpose, retention period, who can access, and how to withdraw.
• Record consent version, timestamp, IP, device, and language shown.
• Withdrawal immediately disables verification, schedules template deletion, and offers the manual route.
• Minors or special cases: the institution can require guardian consent; model this in the consent record.
• Re-consent is required when the consent version or purpose changes.
5.2 Enrollment
1. Authenticated user reads the notice and gives consent.
2. Guided capture of 5 to 8 samples across pose and expression, with real-time guidance (too dark, too far, face covered, multiple faces).
3. Quality gates: face size, sharpness, brightness, pose angle, occlusion, single face.
4. Liveness is checked during enrollment too, so spoofed photos cannot become the template.
5. Generate embeddings, drop raw frames from memory, store the template encrypted (AES-256-GCM with envelope encryption, key version recorded).
6. Duplicate-enrollment check against other consented templates in the same institution, flagged for human review rather than auto-rejected.
7. Template carries model version, template version, quality score, and expiry.
5.3 Verification
1. Authenticated user selects an active session they are eligible for.
2. Client captures a short burst of frames with a randomised challenge (turn left or right, look up, smile, or read a digit sequence).
3. Server checks: exactly one face, quality, liveness, challenge completion, frame timing consistency.
4. Embedding compared one-to-one with the user's active template using a per-institution calibrated threshold.
5. Outcome: verified, rejected or manual_review, each with a confidence score and reason codes. A grey band between two thresholds routes to review.
6. Only verified can create a present or late record, and the server writes the timestamp.
7. Rate limits and lockouts: repeated failures trigger cooldown and alert the faculty or admin.
5.4 Presentation-Attack Detection
Layer several signals; never rely on blink detection alone: active challenge-response, passive texture and moire analysis, screen and print artefact detection, depth and parallax cues from head movement, frame-sequence consistency, and device-side signals (Play Integrity, camera-injection and virtual-camera detection). Document known limitations, build a spoof test kit (printed photo, phone replay, tablet replay, mask where lawful and consented), and report APCER and BPCER.
5.5 Model Governance (new)
• model_versions registry with checksum, licence, evaluation metrics, and rollout status.
• Shadow mode: run a candidate model alongside the active one and compare, without affecting results.
• Re-enrollment campaigns when a model change requires new templates.
• Evaluation harness producing FAR, FRR, EER, ROC and DET curves, with per-condition breakdowns (lighting, camera, glasses, demographics where lawfully collected) to detect bias.
5.6 Privacy Compliance (new)
• Treat biometric data as sensitive personal data. Design for India's DPDP Act 2023 and be adaptable to GDPR-style requirements; get legal review before launch.
• Provide a DPIA template, a data-flow diagram, a retention schedule, and a breach-response runbook in docs/.
• Data subject tools: export my data, delete my biometrics, withdraw consent, view who accessed my data.
• Automatic retention jobs: expire templates after graduation, separation or inactivity.
6. Attendance Engine
6.1 Types and Statuses
Types: Student, Faculty, Staff, Class, Event, Laboratory, plus Exam Hall and Workshop or Seminar (new). Statuses: Present, Absent, Late, Half Day, On Duty, Leave, Holiday, Excused, plus Pending Review and Manual (new).
6.2 Sessions
Fields: session ID, institution, academic year, department, course, semester, section, subject, faculty, room, date, start, end, grace period, status, mode (face, QR plus face, manual), and policy snapshot. Lifecycle: scheduled, open, paused, closed, cancelled. Only faculty with the right scope can transition states, and every transition is audited.
6.3 Rules
• One valid record per person per session, enforced by a unique constraint plus transactional upsert logic and idempotency keys, tested under concurrent load.
• Validate session state and time window, eligibility via enrollment, and server-side timestamps only. No backdating.
• Configurable late rules and per-institution policy for how late, OD, leave and excused count.
• Cancelled sessions and holidays are excluded from the denominator.
• Formula: Attendance % = (eligible present-equivalent sessions / total eligible sessions) x 100.
• Correction workflow: request, reason, evidence upload, HOD or Principal approval, immutable audit trail, notification.
6.4 Anti-Proxy Controls (new)
Combine, per institution policy: rotating session QR or short code displayed in class, geofence or campus Wi-Fi allowlist, BLE classroom beacon proximity, device binding (one primary device per user, approved change flow), mock-location and rooted-device detection, impossible-travel checks, and anomaly alerts (same device marking for several users, repeated borderline scores, odd time patterns).
6.5 Timetable and Scheduling (new)
Weekly timetable builder with rooms, periods, clash detection, substitute faculty, swaps, auto-generation of sessions, holiday calendar integration, and faculty reminders.
6.6 Leave, On-Duty and Condonation (new)
Leave and OD request workflows with document upload and multi-level approval, auto-applied to affected sessions. Configurable shortage thresholds (for example 75%), condonation requests, exam-eligibility reports, and warning ladders.
6.7 Kiosk Mode (new, opt-in)
A registered, locked-down tablet at a gate or lab for staff check-in and check-out. Because no login precedes the scan, restrict matching to an opted-in cohort, require explicit institutional policy and consent, apply stricter thresholds, and log every match. Disabled by default.
6.8 Manual Route
Always available, always audited: faculty mark with mandatory reason, or student request with approval. Manual records are labelled and reportable so they can be reviewed for misuse.
7. Academic Management
Institutions, departments, courses, academic years, semesters, sections, students, faculty, staff, subjects, faculty-subject mapping, enrollments, rooms (new), batches and lab groups (new), holidays and events (new), and promotion or year rollover (new).
Bulk import (CSV and Excel): downloadable templates, dry-run validation, row-level error report, idempotent re-import, and rollback of the last import.
8. Database
PostgreSQL, UUID primary keys, foreign keys, check constraints, indexes, created_at, updated_at, soft delete where appropriate. Alembic migrations only; no manual schema edits.
Core tables (from v1): institutions, users, roles, permissions, role_permissions, user_roles, departments, courses, academic_years, semesters, sections, students, faculty, staff, subjects, faculty_subjects, enrollments, biometric_consents, biometric_templates, face_enrollment_sessions, attendance_sessions, attendance_records, attendance_devices, attendance_correction_requests, leave_requests, holidays, notifications, audit_logs, refresh_tokens, system_settings, model_versions.
Additional tables (new): rooms, timetable_entries, parent_links, guardian_consents, verification_attempts (scores and reason codes, no images), liveness_events, device_bindings, session_qr_tokens, import_jobs, import_errors, report_jobs, api_keys, webhooks, webhook_deliveries, outbox_events, idempotency_keys, retention_policies, data_subject_requests, feature_flags, condonation_requests, anomaly_alerts.
Key constraints
• UNIQUE (session_id, user_id) on attendance_records.
• Partial unique index: one active template per user per model version.
• Row-level security or enforced tenant filters on every tenant table.
• Append-only audit_logs (no update or delete privileges for the app role), with hash chaining for tamper evidence.
• Encrypted fields are never selected by default in ORM queries.

12. Security
• Authentication: Argon2id, short-lived JWT access tokens, rotating refresh tokens with reuse detection, secure logout and revoke-all, optional TOTP MFA (mandatory for admin roles), brute-force protection, password policy and breach-list check.
• Authorization: central policy engine, institution isolation, department and section scoping, resource-level checks, deny by default.
• Biometric security: encryption at rest and in transit, envelope encryption with key rotation, templates unreadable by the API role except through the biometric service, no biometric payloads in logs or error trackers, no public biometric endpoints, access logging.
• Application security: HTTPS and HSTS, CORS allowlist, CSRF protection if cookies are used, security headers and CSP, SQLi and XSS prevention, secure uploads (type, size, malware scan hook), request size limits, SSRF protection on webhooks, signed webhook payloads.
• Supply chain: pinned dependencies, pip-audit, npm audit, Trivy on images, secret scanning, SBOM generation, Dependabot.
• Deliverables: threat model (STRIDE), abuse-case list, security test plan, and a pre-launch penetration-test checklist in docs/security.md.

Configurable filters, scheduled reports by email, Excel, PDF and CSV exports, printable layouts, and asynchronous generation for large reports.

16. Testing and Quality Gates
• Backend: unit, API, database, authorization matrix, tenant isolation, concurrency and duplicate prevention, attendance math (including boundary and policy variants), consent withdrawal, idempotency, migration tests. Coverage of at least 85% on services.
• AI: detection, enrollment quality, FAR and FRR at the chosen threshold, lighting, camera, pose and glasses variations, spoof tests (print, replay, mask where lawful), regression test on every model change.
• Frontend: component, form validation, route guards, role-based UI, API integration (MSW), Playwright E2E, accessibility checks.
• Android: permission flows, auth, verification flow, network failure, device compatibility, UI tests.
• Non-functional (new): load test (k6 or Locust) at a realistic peak such as 2,000 simultaneous marks at period start; p95 latency target for verification; chaos test for Redis and worker outages.
• Gates: no merge unless lint, types, tests and security scans pass.
